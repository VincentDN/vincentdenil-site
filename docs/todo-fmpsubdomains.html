Flagmaker Subdomain Rollout

Two hidden static subdomains under flagmaker-print.com. Different access posture, same isolation rules. Read the whole thing before opening either repo.

Ground rules — both builds

  • One GitHub repo per subdomain, nothing shared with the main site or Shopify theme repo. Never commit to any repo outside the one you were assigned.
  • Hosting is Cloudflare Pages, connected directly to the GitHub repo (git-integrated deploy). No build step, no Cloudflare API token needed to ship — push to the branch, Pages deploys it.
  • Every page ships an HTML <meta name="robots"> noindex tag, a _headers file, and a robots.txt — exact contents below. No page goes live without all three.
  • Nothing here touches the DNS records for @ or www — those stay on Shopify, untouched.

Crew scope: repo content, folder structure, headers/robots config, PRs.
Admin-only: Cloudflare Pages project, custom domain, DNS, Access policy.

The two builds

ops.flagmaker-print.com Password gated

repo: flagmaker-ops

  1. Build the static pages as normal HTML under whatever folder structure fits ops content. No login form needed in the code — gating happens at the network edge, not in the page.
  2. Ship the noindex meta tag, _headers, and robots.txt from the snippets below.
  3. Do not build your own password screen or client-side JS check. That's not real security and it isn't the plan here — leave the login gate to Cloudflare Access, set up by admin after your repo is connected.
  4. Once your PR merges to the deploy branch, tell admin — they wire up the custom domain and Access policy on their end. Confirm with them before treating this as live.
studio.flagmaker-print.com Unlisted, no login

repo: flagmaker-studio

  1. No index page. Root path should 404 or show a blank generic placeholder — never a page that lists or links to other pages here.
  2. No links between pages, no shared nav, no sitemap.xml. Each page stands alone and is reachable only by whoever was given its exact URL.
  3. Use a long unguessable path per page, not a readable slug — e.g. /p/9f2a7c-acme, not /acme. Treat the URL itself as the access control.
  4. No analytics or third-party embeds on these pages. Any script that logs referrers or is publicly queryable can leak the URL you're relying on staying secret.
  5. Same noindex meta, _headers, and robots.txt as ops — ship them here too.

No password = anyone who gets a link can view it forever, and links leak (screenshots, forwarded emails, browser history sync). This is obscurity, not access control. Don't put anything on studio you'd mind becoming public — flag it back to admin if a page needs real protection instead.

Config snippets — ship on both repos

In every page's <head>

<meta name="robots" content="noindex, nofollow, noarchive">

/_headers — repo root, Cloudflare Pages reads this automatically

/*
  X-Robots-Tag: noindex, nofollow

/robots.txt — repo root

User-agent: *
Disallow: /

Before you call either one done

    Questions on scope or access → ask admin before improvising. Don't request a Cloudflare or Shopify login to get either build done — if a task seems to need one, that's a sign it belongs to admin, not crew.
